## 一、原提示词诊断

原始需求：

> 在这个文件夹下面新创建一个 yuanyu 的文件夹，采用技术栈可选：SpringBoot+Vue3 / SpringCloud 微服务 + Redis + MQ + 大数据组件 / Python 深度学习 + Web 前端 / UniApp 小程序 + AI 接口这些市面上的主流框架，帮我完成基于 YOLO 的工地安全行为实时检测预警系统这个毕业设计项目，首先帮我进行提示词优化。

| # | 问题 | 造成的后果 | 优化方向 |
|---|------|-----------|---------|
| 1 | 技术栈用 `/` 并列，给了 4 套互斥方案 | AI 会把 SpringCloud、Hadoop、UniApp、PyTorch 全塞进来，最后跑不起来 | 明确「一套主方案 + 可选加分项」，并说明取舍理由 |
| 2 | 没有角色设定和交付标准 | 输出停留在「方案介绍」，不给可运行代码 | 设定「资深 CV + 全栈工程师 + 毕设导师」角色，定义 DoD |
| 3 | 业务边界模糊 | 不知道检测哪些行为、告警怎么触发、谁来处理 | 用 P0/P1/P2 分级列功能，明确不做什么 |
| 4 | 完全没有提数据集和模型 | 这是最容易翻车的部分，AI 会假设权重已存在 | 指定公开数据集、类别体系、训练与评估指标 |
| 5 | 没有性能与验收指标 | 无法判断「做完了没有」 | 给出 FPS、延迟、mAP、并发等可测指标 |
| 6 | 没有阶段划分 | 一次性生成上万行代码，质量不可控 | 拆成 11 个阶段，每阶段可运行、可验证 |
| 7 | 没约束运行环境 | 无 GPU 时直接跑不起来 | 要求 CPU 可降级、Docker Compose 一键启动 |
| 8 | 只想要「系统」 | 毕设还要开题、论文、PPT、演示视频 | 交付物清单里加入文档与答辩材料 |
| 9 | 没有防幻觉约束 | AI 编造数据集路径、模型权重、第三方接口 | 明确「不确定先问，不许编造」 |

**优化原则：角色化 → 结构化 → 约束化 → 阶段化 → 可验收 → 可回退。**

## 二、主提示词（可直接复制给 AI）

```text
# 角色
你是一名资深计算机视觉工程师 + Java/Vue 全栈工程师，同时有 5 年本科毕业设计指导经验。
你要独立完成一个「可运行、可演示、可写论文」的毕业设计项目，而不是只给方案。

# 项目名称
基于 YOLO 的工地安全行为实时检测预警系统

# 业务背景与目标
建筑工地安全事故高发，传统人工巡检存在盲区大、响应慢、无法追溯的问题。
本系统接入工地摄像头视频流，利用 YOLO 实时识别不安全行为，在 2 秒内生成带截图的告警，
推送到管理端并支持处置闭环，实现「看得见、报得快、查得到、管得住」。

# 技术栈（固定，不要替换；无 GPU 时必须能降级到 CPU 运行）
- 算法服务：Python 3.10、PyTorch 2.x、Ultralytics YOLOv8、OpenCV、ByteTrack、FastAPI、ONNX
- 业务后端：Java 17、Spring Boot 3.2、MyBatis-Plus、Spring Security + JWT、
            WebSocket(STOMP)、Redis、RabbitMQ、MySQL 8
- 前端：Vue 3 + Vite + TypeScript + Pinia + Vue Router + Element Plus + ECharts + video.js
- 部署：Docker Compose + Nginx；开发环境兼容 macOS(Apple Silicon) 与 Windows

# 功能范围
P0 必须实现：
1. 视频源管理：支持 RTSP、本地视频文件、USB 摄像头、浏览器摄像头四种输入
2. 实时检测：安全帽佩戴/未佩戴、反光衣穿着/未穿着、人员；画面叠加检测框与类别
3. 多目标跟踪：ByteTrack 分配 trackId，同一人同一行为不重复告警
4. 区域规则：支持在画面上绘制多边形 ROI，配置「危险区域入侵」「电子围栏」
5. 告警引擎：置信度阈值 + 连续 N 帧确认 + 冷却时间 + ROI 四重过滤，生成告警记录并保存截图
6. 实时推送：WebSocket 推送到前端，弹窗 + 声音 + 告警列表实时刷新
7. 告警处置：确认 / 误报 / 已整改 三种状态，记录处理人、时间、备注，形成闭环
8. 统计报表：按时间、行为类型、摄像头、工地维度统计，ECharts 图表 + Excel 导出
9. 基础管理：登录、用户、角色权限、工地、摄像头、检测区域、告警规则、操作日志
10. 实时监控页：多路画面切换、检测框叠加、FPS/延迟/今日告警数指标卡

P1 加分（时间允许再做）：
- 可视化大屏（工地分布、告警趋势、行为排行、实时滚动）
- 模型版本管理与热切换（记录 mAP、推理耗时）
- 吸烟、打电话、跌倒、烟火检测（任选 1-2 类）
- 告警通知渠道：邮件 / 企业微信或钉钉 Webhook
- UniApp 小程序：告警列表、告警详情、一键处置
- 接入大模型 API 自动生成《每日安全巡检日报》（可插拔，失败时降级为模板）

P2 选做（不影响答辩主线）：
- ONNX/TensorRT 加速、模型剪枝量化
- Flink/ClickHouse 做检测记录实时统计
- Jetson 边缘部署

明确不做：人脸识别与身份绑定、跨摄像头 ReID、BIM 数字孪生、真实工地长期驻场部署。

# 算法与数据要求
- 类别体系：person、helmet、no_helmet、vest、no_vest（P1 可扩展 smoking、phone、fall）
- 数据集：优先 SHWD（安全帽，约 7.5k 张）+ Roboflow Construction Site Safety（含反光衣）；
  另提供 200 张自建数据的采集与标注脚本（Label Studio / labelImg）
- 划分 8:1:1，数据增强：Mosaic、MixUp、HSV、翻转、随机裁剪
- 训练：yolov8n 起步（CPU 可跑），有 GPU 用 yolov8s；imgsz=640，100~200 epochs
- 评估：mAP@0.5、mAP@0.5:0.95、Precision、Recall、F1、FPS、混淆矩阵、PR 曲线
- 对比实验：YOLOv5s / YOLOv8s / YOLO11s 至少三组；改进点（注意力、小目标头、轻量化）作为消融实验
- 目标：安全帽 mAP@0.5 ≥ 0.85，召回 ≥ 0.90，单路 1080p 抽帧推理 GPU ≥ 15 FPS / CPU ≥ 3 FPS

# 架构约束
1. 算法服务与业务服务物理分离：Python 负责拉流、推理、跟踪、规则判定；
   Spring Boot 负责业务、权限、告警落库、统计与推送；两者用 HTTP + RabbitMQ 通信。
2. 告警链路必须是：检测 → 规则过滤 → MQ 事件 → 业务落库 → WebSocket 推送，禁止在 Python 里直接写业务库。
3. 所有外部依赖（数据库、Redis、MQ、模型路径、RTSP 地址）必须外置到配置文件/环境变量。
4. 单机执行 docker compose up -d 能启动全部中间件与应用；无摄像头时用示例视频演示。
5. 前端不能硬编码后端地址，统一走 Vite 代理与环境变量。
6. 代码必须完整可运行，禁止伪代码、禁止 TODO 占位、禁止引用不存在的包或接口。

# 交付物
1. 源码：ai-service / backend / frontend / deploy 四个目录，含 Dockerfile 与 compose
2. 数据库：init.sql（建表 + 索引 + 演示数据）、ER 图
3. 文档：README（一键启动）、架构设计、数据库设计、接口文档（OpenAPI）、部署文档
4. 论文素材：章节框架、系统架构图、用例图、ER 图、流程图、算法对比表、测试用例表
5. 答辩材料：PPT 大纲（15~18 页）、8 分钟演示脚本、高频答辩问题及参考答案
6. 测试：接口测试用例、算法评估报告、2 小时稳定性测试记录

# 工作方式（重要）
1. 第一轮只输出《需求确认 + 系统架构 + 模块划分 + 数据库设计 + 接口清单》，等我确认后再写代码。
2. 之后按阶段交付，每个阶段必须是「可启动、可验证」的最小闭环，禁止一次性输出全部代码。
3. 每轮回复固定包含六部分：
   ① 本阶段目标  ② 变更文件清单  ③ 完整代码  ④ 启动与验证命令（含预期输出）
   ⑤ 已知限制与排错  ⑥ 下一阶段建议
4. 涉及数据集下载、模型权重、第三方密钥时，先说明获取方式与替代方案，不许编造链接。
5. 不确定的需求先提问，不要自行假设后继续。

# 验收标准（Definition of Done）
- [ ] docker compose up -d 后 6 个服务全部 healthy
- [ ] admin/123456 可登录，RBAC 权限生效
- [ ] 新增摄像头（本地视频）后 10 秒内出画面与检测框
- [ ] 模拟未戴安全帽，2 秒内产生告警、截图可访问、前端弹窗
- [ ] 同一人持续违规 1 分钟内只告警 1 次（冷却生效）
- [ ] 告警可处置，状态与统计同步更新
- [ ] 统计页数据与数据库一致，Excel 可导出
- [ ] 断网/断流后自动重连，服务不崩溃
- [ ] README 按步骤可复现，无缺失配置
- [ ] 算法评估报告含 mAP、P、R、F1、FPS 与对比实验
```

## 三、这段提示词为什么这样写

| 设计 | 作用 |
|------|------|
| 角色 + 经验设定 | 让模型进入「交付者」而非「咨询者」模式，输出代码而非泛泛而谈 |
| 固定技术栈 | 消除多方案摇摆，避免 SpringCloud + Hadoop + UniApp 堆砌导致的不可运行 |
| P0/P1/P2 分级 | 保底能答辩，加分项可裁剪，防止范围蔓延 |
| 明确「不做」 | 人脸识别、ReID、数字孪生是常见跑题点，提前封死 |
| 数据集与指标 | 把最容易失败的部分前置，模型效果可量化、可写进论文 |
| 架构约束 | 强制「算法/业务分离 + MQ 解耦」，这是答辩时的技术亮点 |
| 六段式输出 | 每轮都可复现、可排错，避免「代码给了但跑不起来」 |
| 先设计后编码 | 先对齐需求与表结构，减少后期大改 |
| 防幻觉条款 | 数据集链接、依赖版本、第三方接口是 AI 编造重灾区 |

## 五、技术选型对比与推荐

### 5.1 三套方案

| 维度 | 方案 A：混合架构（推荐） | 方案 B：Python 全栈（轻量） | 方案 C：SpringCloud 微服务（重型） |
|------|------------------------|---------------------------|-----------------------------------|
| 组成 | Spring Boot 业务 + Python 算法 + Vue3 | FastAPI 业务与算法一体 + Vue3 | Nacos/Gateway/OpenFeign/Sentinel + Python 算法 |
| 工作量 | 大（但可分阶段） | 小 | 很大 |
| 技术亮点 | 算法/业务解耦、MQ、WebSocket、RBAC | 开发快、链路短 | 微服务治理、服务发现、熔断 |
| 答辩说服力 | 强，能讲架构 | 中，偏「课设」 | 强，但容易被追问部署与运维 |
| 单人风险 | 中 | 低 | 高 |
| 适合 | 想拿良/优、时间 10~12 周 | 时间紧、只求稳过 | 学校明确要求微服务、有队友 |

**推荐方案 A。** 理由：

1. 毕设评分看「工作量 + 技术难度 + 完整性」，A 同时覆盖深度学习、后端、前端、中间件、部署。
2. 算法与业务分离是真实工程做法，答辩时能讲清楚「为什么不用一个 Flask 全包」。
3. 保留降级路径：时间不够时把 Spring Boot 换成 FastAPI（方案 B），前端与算法代码可复用。

### 5.2 关于原提示词里的「大数据组件」和「SpringCloud」

- **大数据组件**：Hadoop/Spark 与「实时检测」关系不大，硬上会增加 3~4 天环境成本且答辩讲不透。
  若要体现数据能力，建议 P2 加 **ClickHouse 存检测记录 + Flink 做分钟级统计**，或直接用 MySQL 聚合 + Redis 缓存，够用且稳。
- **SpringCloud**：完整微服务需要 Nacos、Gateway、Sentinel、OpenFeign、链路追踪，单人部署极易翻车。
  推荐「模块化单体 + 独立算法服务」作为微服务雏形；学校硬性要求时，最小拆分为 gateway / business / ai 三个服务即可。
- **UniApp**：作为 P1 加分项，只做告警查看与处置，2~3 天可完成，不要做成第二套完整系统。
- **AI 接口**：建议只用于「巡检日报/告警摘要」这类锦上添花的能力，必须可插拔、可降级，不能成为主链路依赖。

## 十三、答辩高频问题预判

1. **为什么选 YOLOv8，而不是 Faster R-CNN / YOLOv5？**
   单阶段 anchor-free，速度与精度平衡好；Ultralytics 生态完善，导出 ONNX/TensorRT 方便；与 v5 相比结构更简洁、易部署。
2. **小目标和遮挡怎么处理？**
   提高输入分辨率、Mosaic/MixUp 增强、ByteTrack 跨帧补偿、连续帧投票；极端遮挡明确为局限性。
3. **误报怎么抑制？**
   置信度阈值 + 连续 N 帧 + ROI 区域 + 冷却时间四重过滤，再加人工误报反馈调参。
4. **实时性怎么保证？**
   抽帧推理、半精度、异步流水线、批量推理、ONNX/TensorRT；算法与业务解耦，MQ 削峰。
5. **数据集多大？怎么划分？类别是否均衡？**
   说明来源、数量、8:1:1 划分、类别分布与欠采样/加权策略。
6. **创新点是什么？**
   ① 检测+跟踪+区域规则融合的告警引擎；② 四重误报抑制；③ 轻量化模型边缘部署；④ LLM 自动生成巡检日报。
7. **告警会不会丢？**
   MQ 持久化 + 手动 ACK + 重试 + 死信队列 + alarmNo 幂等。
8. **系统能支持多少路？**
   给出实测数据与瓶颈分析（解码、推理、带宽），说明横向扩展方式（多算法实例 + 负载均衡）。
9. **隐私合规怎么考虑？**
   仅识别安全行为不识别身份，本地部署，截图访问鉴权，可配置人脸模糊。
10. **和商用系统的差距？**
    商用胜在算法精度与硬件生态；本系统胜在低成本、可定制、可二次开发，适合中小工地。

## 附录 D：提示词使用小贴士

1. **先设计后编码**：阶段 0 的产出一定要人工过一遍，表结构和接口定错，后面全是返工。
2. **小步验证**：每阶段结束必须亲手跑一遍命令，不要相信「应该可以」。
3. **报错原文回贴**：把完整堆栈贴给 AI，比描述「报错了」有效 10 倍。
4. **控制上下文**：长项目每阶段开新会话，附上「项目现状摘要 + 本阶段目标」。
